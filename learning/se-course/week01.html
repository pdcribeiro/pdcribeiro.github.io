“Correctness is not what the code does; it is what the spec says it should do.”

The Contract Analogy

Caller (client) and Implementer (supplier) sign a contract.

  • Caller must meet the preconditions.
  • Implementer guarantees postconditions and invariants.

Protects both sides:

  • Caller knows what to expect.
  • Implementer knows what they can assume.

⚡ Without a spec, testing only catches surface errors. With a spec, you can reason compositionally.

Real Bug: Ariane 5

Flight 501 – reused spec from Ariane 4 without checking horizontal bias preconditions.

  • Overflow in a 64-bit conversion.
  • Rocket self-destructed 37 seconds after launch.
  • The code “worked” in the old context but violated the new spec’s implicit assumptions.

💡 Lesson: Specifications must be explicit, precise, and revisited when the environment changes.

Pre / Post Syntax

Java-style with JML annotations (@requires, @ensures).

/**
 * @requires x >= 0
 * @ensures Math.abs(result - Math.sqrt(x)) < 1e-9
 */
public double sqrt(double x);
  • @requires – what must be true before the call.
  • @ensures – what the method guarantees after, if preconditions are met.

If a caller violates a precondition, behavior is undefined (or an exception is thrown).

findMax Spec

/**
 * @requires arr != null && arr.length > 0
 * @ensures forall i in [0, arr.length-1] :: result >= arr[i]
 * @ensures exists i in [0, arr.length-1] :: result == arr[i]
 */
public int findMax(int[] arr);

Why non‑null and non‑empty? (No maximum over an empty set.)

✅ Implementation may throw NullPointerException / IllegalArgumentException defensively – still meets the spec.

Class Invariants

A property that must hold for every instance of the class at all times between public method calls.

  • bankAccount.balance >= 0
  • date.month in 1..12
  • SortedList: list[i] <= list[i+1]

Enforced in:

  • Constructor – establishes the invariant.
  • Every public mutator – checks/repairs at the end.

Private helpers may temporarily break invariants, but public methods must restore them.

❌ BAD: No Invariant

public class BankAccount {
    private int balance;

    public BankAccount(int initial) {
        balance = initial;   // no check!
    }
    public void withdraw(int amount) {
        balance -= amount;   // can go negative
    }
    public void deposit(int amount) {
        balance += amount;
    }
    public int getBalance() { return balance; }
}

⚠️ Client can withdraw more than available – violates business rule.

✅ Fixed: Invariant Enforced

We add checkInvariant() and call it after every mutation.

public void withdraw(int amount) {
    if (amount > balance) {
        throw new IllegalArgumentException();
    }
    balance -= amount;
    // ❌ no invariant check
}

After withdrawal, the invariant might still hold, but we are not verifying it.

public void withdraw(int amount) {
    if (amount > balance) {
        throw new IllegalArgumentException();
    }
    balance -= amount;
    checkInvariant();  // ✅ crucial!
}

private void checkInvariant() {
    assert balance >= 0 : "balance negative";
}

✅ Invariant checked at the end of every public method (including constructor).

Static vs. Dynamic Checking

🔍 Static
  • Compile‑time
  • Type safety, nullness
  • Zero runtime cost
  • Conservative
⚡ Dynamic
  • Runtime (assert)
  • Semantic properties
  • Only as good as tests
  • Can be disabled

Use static for structure; dynamic for business rules.

Assertions vs. Exceptions

  • assert – for internal invariants; can be disabled; indicates programmer error.
  • IllegalArgumentException – for input validation from untrusted external callers.

🚫 Never use assert to validate user input – it may be turned off in production.

Eiffel (Bertrand Meyer) has language‑level support for Design by Contract.

Specification Strength

A spec S2 is stronger than S1 if:

  • S2’s precondition is weaker (more callers), OR
  • S2’s postcondition is stronger (more guarantees).
Spec A (partial) @requires x >= 0
Spec B (total) @requires true
◄──── WEAKER PRECONDITION = STRONGER SPEC ────►
Easier to implement Easier to call

Weaker precondition → stronger spec → harder to implement.

Common Pitfalls

❌
Over‑specifying (leaking implementation)
Bad: @ensures result == sortedCopy(arr)[0]
Good: @ensures result >= all elements
❌
Forgetting to check invariants after every public method
Even getters that return mutable objects can break invariants.
❌
Using assert for public input validation
Assertions can be disabled → use IllegalArgumentException for public APIs.
❌
Confusing pre with post
@requires result > 0 is wrong – result belongs in @ensures.
